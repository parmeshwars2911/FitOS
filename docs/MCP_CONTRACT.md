# FitOS MCP contract

FitOS should expose **derived, user-scoped fitness context**, not raw unrestricted database access.

## Authentication boundary

- Every MCP request must resolve to an authenticated FitOS user.
- The backend must authorize with the end user's identity and preserve Supabase RLS semantics.
- Never expose the Supabase service-role key to an MCP client or mobile app.
- A publishable key is not authorization; user access is controlled by the user's short-lived access token and RLS.

## V1 read scope

The initial MCP server should be read-only and expose one stable tool:

### `fitos_get_coach_context`

Returns the latest cloud revision plus the deterministic `CoachContext` and `WeeklyReview` already generated by FitOS.

Suggested response:

```json
{
  "revision": 12,
  "updatedAt": "2026-09-09T12:00:00Z",
  "schemaVersion": 1,
  "coachContext": {},
  "weeklyReview": {}
}
```

The MCP server may also expose a resource containing the complete `CloudStateSnapshot` for user-authorized deep analysis, but tools should prefer the smaller coach context when possible.

## Write scope

Do **not** enable MCP writes in V1. Future write tools such as nutrition logging or workout creation should require a distinct write scope and explicit confirmation before mutation.

## Versioning

`CloudStateSnapshot.schemaVersion` is the compatibility boundary. MCP code must reject unknown future versions rather than silently guessing field semantics.

## Conflict model

The cloud row uses an integer revision. Clients commit with `expectedRevision`; stale writes fail with `revision_conflict`. A client must pull the newer state and reconcile rather than overwriting it blindly.

## Privacy

HealthKit-derived values can be included only because the user explicitly synchronized them into FitOS. External AI access should be separately opt-in and revocable; cloud sync alone must not imply MCP sharing permission.
